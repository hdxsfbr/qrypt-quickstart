400"'size' must be an integer between 1 and 512"size is 0, over 512, or not a number; often someone passed a byte count (e.g. 32) thinking size is in bytes.Use size=1; it returns 1,024 bytes. Slice 32 bytes for AES-256.

503Entropy temporarily insufficientQrypt's entropy supply is briefly low.Try again shortly, with a delay. Don't loop.

Common mistakes

  • Retrying in a loop after a 429. Wait 10 s or more; live can rate-limit after one prior call.
  • Using the base64 string as the key instead of decoding it.
  • Treating size as bytes.
  • Reusing the same entropy bytes for two keys.
  • Printing the key or token while debugging, or committing .env.
  • Leaving out Accept: application/json (the docs require it).
  • Assuming an SDK package exists; the API is plain HTTPS.

Codex: bwrap: loopback: Failed RTM_NEWADDR

Symptom: in Codex, every shell command and web fetch fails before it runs with bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted. The agent never reaches this quickstart.

Cause: Codex's Linux sandbox uses bubblewrap (bwrap), which needs unprivileged user namespaces (an isolated view of the system that a normal user can create). Ubuntu 23.10, 24.04 and later set kernel.apparmor_restrict_unprivileged_userns=1, so AppArmor (Ubuntu's security module) blocks them unless a profile allows bwrap.

Fix (OpenAI's documented steps, needs sudo): install the system bwrap; on Ubuntu 24.04 also load its AppArmor profile, then test:

sudo apt update
sudo apt install bubblewrap apparmor-profiles apparmor-utils
sudo install -m 0644 \
  /usr/share/apparmor/extra-profiles/bwrap-userns-restrict \
  /etc/apparmor.d/bwrap-userns-restrict
sudo apparmor_parser -r /etc/apparmor.d/bwrap-userns-restrict
codex sandbox -- /bin/true   # no output, exit 0 = fixed

The test command is for codex-cli 0.162.1, where codex sandbox takes the command directly (check codex sandbox --help on other versions). Codex then works with its sandbox on, for example codex exec --sandbox workspace-write.

OpenAI lists sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0 only as a fallback. It turns the protection off for every program on the machine, so prefer the profile. Another option is Isolated Setup: Docker is then the boundary, and the token stays on the host. Codex's own sandbox cannot start inside that container, because Docker also blocks user namespaces; the container is the sandbox there.

Do not use --dangerously-bypass-approvals-and-sandbox on your own machine to get past this. It turns off Codex's sandbox and approvals, so the agent can read any file, including .env and other secrets, and reach the network freely.

Sources: OpenAI Codex docs, Sandbox: Prerequisites; openai/codex issue 14919; openai/codex pull request 14963.

Proxy and TLS setup commands

Python (requests reads these variables):

export HTTPS_PROXY=http://proxy.example.com:8080
export REQUESTS_CA_BUNDLE=/path/to/company-ca.pem
python quickstart.py

Node 24 and later:

export HTTPS_PROXY=http://proxy.example.com:8080
export NODE_EXTRA_CA_CERTS=/path/to/company-ca.pem
NODE_USE_ENV_PROXY=1 node quickstart.mjs

Node 20 and 22 (built-in fetch ignores HTTPS_PROXY): run npm i undici, then add these two lines at the top of the script:

import { setGlobalDispatcher, EnvHttpProxyAgent } from "undici";
setGlobalDispatcher(new EnvHttpProxyAgent()); // honors HTTPS_PROXY

Expected error body from the API, for reference:

{"error": "Forbidden or entropy quota reached"}
